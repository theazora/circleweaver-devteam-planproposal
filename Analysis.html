4. spring2 in detail

spring2/ is the big one from my walkthrough: about 193 JSP files that make up the current UI. Each subfolder is basically a section of the product. When we port to React together, we don’t need a matching file for every JSP on day one. We just need to agree which area of the app each screen belongs to.

Modals and partials mostly live in new_assets/templates/ (HTML + Angular controllers). Those can become React components one dialog at a time after we have wireframes, not during the file-move months.

Learning tip: WrapLearning.jsp already reads video IDs like Tutorial09a and links out to the static site. So tutorials already behave like content with stable IDs. In the new app they fit better as profile / learning posts than as a pile of HTML pages.

5. Bootstrap + AngularJS (overall analysis)

The current UI is server-rendered JSP shells with AngularJS 1.x on the client, plus Bootstrap (and a lot of hand-coded CSS scattered across the WAR). That setup has kept collaboration features running for a long time. From what I’ve worked with before, my advice is we mainly change how the front end is built so it’s easier to maintain and teach, while keeping the same product behavior as we work through this together.

Once UI/UX hands over wireframes from Figma, we do not have to recreate every layout by hand from screenshots. With Figma’s Pro features (we have access through the educational plan, which is the full version), we can use Figma extensions and widgets to pull design tokens, spacing, and components closer to our React code and port screens more directly. We do not need to lock the exact toolchain yet; the point is the designs can move into the app faster than rewriting all that old CSS by eye.

What workedWhere it slows us down now
Fast to add another JSP + Angular controller for a feature Harder to share one design system; mobile got a second path (wmf/)
Bootstrap gave consistent buttons/forms quickly Lots of hand CSS on top; versions and copies drifted across WAR folders
AngularJS two-way binding felt great for forms/modals AngularJS is end-of-life; hiring / teaching it is awkward for a novice team
Everything ships inside one WAR (simple ops story once) Frontend and backend release as one blob; duplicates (TinyMCE ×2) pile up
Bottom line from my analysis: Bootstrap + AngularJS was a reasonable way to ship the product when it was built. React + Next.js looks like a better fit for this team now, and for people who continue on the project later: easier to learn, easier to match new UI/UX work from Figma, and one mobile-first UI instead of parallel paths. Same meetings, topics, and roles; we’d just put clearer components and TypeScript around them as we build together.

7. What I’d wait on until after November

From where I’m standing, spring2, new_assets, and the workspace screens are where most of the CSS and TypeScript page work will end up in the new app. My recommendation is that we wait for design on that instead of inventing layouts now, then build those screens together.

What we could focus on until ~Nov 13: inventory, moving tutorials/marketing into content, removing obvious duplicates, Next backbone + API proxy, and stakeholder questions (SSO vs OAuth, richer profiles, hosting).

What we could do after wireframes + a11y notes land: visual design, component CSS, TypeScript for meetings / home / profiles, and accessibility passes. I’d hold off deep-editing those presentation files in September and October before the wireframes land.

What I’m aiming for with these first eight weeks of analysis + cleanup: slimmer repo, clearer map, solid backbone, faster day-to-day workflows. Visual polish and accessibility detail come after the handoff. If we leave the structure readable together, whoever stays on the project (or joins next) can pick it up without starting from zero.
